# 近期餐厅榜单：规则与技术选型讨论

更新：2026-11-11。状态：快照表、两级缓存、计算及自动事务发布已完成；服务就绪后异步生成，之后每轮结束等待1小时刷新，单实例防重叠已实现；首页入口及独立榜单页已按确认示意图接入，本地真实接口的空榜与有数据榜单联调已完成，上线验收待进行。缓存已按MySQL→Redis→Caffeine分阶段测量。当前分支：`feature/hot-restaurant-cache`。

本文记录已确认目标、候选规则和待讨论事项。除“已确认”内容外，名称、公式、阈值、刷新间隔及技术方案均为建议，不能视为已定需求或已实现功能；后续讨论直接修订本文。

## 已确认目标

- 面向用户提供餐厅榜单，而不只是缓存餐厅详情。
- 提供近 7×24 小时周榜、近 30×24 小时月榜，每轮生成使用同一个固定截止时刻。
- 首要目标是帮助用户找到真正好吃的餐厅，不能简单把访问量等同于餐厅质量。
- 先讨论并确定详细规则和技术选型，再进行功能开发。

## 已确认规则

- **评分方向：以口味分为主，其他分数为辅。**
- **四维直接加权：口味 70%、性价比 15%、服务 10%、环境 5%。**计算说明见下文。
- **人数通过贝叶斯形式平滑参与排序，周榜、月榜统一 `m = 5`。**`W = (n × R + m × C) / (n + m)`；人数相对 `m` 越少，`W` 越接近参考值 `C`，人数相对 `m` 越多，`W` 越接近真实加权均分 `R`。人数按下述每用户每餐厅一份贡献计算，封禁账号的专项计分规则暂缓。
- **按近期口碑统计：周榜的评分与人数使用过去7×24小时，月榜使用过去30×24小时。**每轮共用微秒精度的截止时刻`T`，计算采用`[T-168/720小时,T)`，包含起点、不含终点；不使用累计人数替代近期人数。
- **首版周榜、月榜均使用固定参考值 `C = 3.5`（五分制）。**尚无真实评价时不生成餐厅评分或榜单名次；开始积累真实评价后使用该参考值计算排序分。用户已决定真实统计基准及切换规则暂缓，积累数据后再讨论。
- **同一用户对同一家餐厅，在对应榜单周期内只计最新一条未删除点评。**对人数 `n` 贡献一人，对均分 `R` 贡献一份评分，反复点评不重复增加权重；周榜和月榜分别计算。删除最新点评后，回退到该周期内上一条未删除点评；没有剩余点评则移除该用户对该餐厅在该榜单中的贡献，不采用周期外点评。
- **周榜、月榜都要求对应周期内至少 3 位不同用户有效计分。**即 `minParticipants = 3`，与平滑强度 `m = 5` 独立；符合条件的餐厅不足展示条数时少展示或空榜，不用人数不足的餐厅补齐。
- **最低评分为对应周期内真实口味均分至少 4.0 分（五分制）。**使用与 `R`、`n` 相同的有效点评计算；同时满足人数和口味门槛后，再按已确认的四维加权及平滑排序分 `W` 排名。
- **榜单仅纳入普通餐厅，食堂和食堂窗口均不参与。**用户考虑食堂数量较少，不为食堂或窗口另设本次榜单。
- **排序顺序为平滑分 `W` 降序、对应周期内有效评价人数 `n` 降序、餐厅 ID 升序。**页面舍入后显示相同不代表计算结果同分；W按精确分子、分母交叉相乘比较，缓存保存已排好序的完整列表。
- **首页设置入口，进入独立榜单页切换近 7 天周榜及近 30 天月榜，各展示前 20 名、不分页。**不足 20 家时少展示或空榜。
- **每项展示排名、封面、餐厅名、对应周期内平滑推荐分和有效评价人数，点击进入餐厅详情。**推荐分使用五分制，来自本周期平滑分W；原始口味均分仍用于入榜门槛。
- **按校区分别生成周榜和月榜，以固定中心点及覆盖半径自动判断餐厅范围。**清水河、沙河半径均为5公里，可分别配置；用户确认沿用既有参考点，坐标及来源见下文校区配置。评价共享，餐厅位于重叠范围可同时参榜。
- **榜单默认每轮结束后等待1小时再后台刷新，间隔保持可配置。**新点评、删除回退及周期到期在下一轮成功刷新后反映到榜单；点评发表、详情及现有 ES 同步按各自流程更新。刷新失败按下文已确认的沿用上限处理，商户快速下榜专项机制暂缓。
- **采用 Caffeine + Redis 两级 Cache Aside（旁路缓存），本机有效期为 30 分钟、可配置。**Caffeine 在本机保存完整榜单对象，Redis String 保存完整 JSON；每个校区、周期一份排好序的结果，包含排名与展示资料。MySQL 新快照实际提交后删除两级缓存，后续读取未命中时加载并回填，不等待本机自然过期；并发保护细节见下文，首期不采用 ZSET + Hash。
- **首期单实例的缓存加载与快照发布共用一把全局本地锁，不按 4 份榜单拆锁。**Caffeine 命中无需加锁，点评聚合及榜单计算放在锁外；具体事务与故障处理边界见下文。
- **MySQL 保留每份榜单最近一次成功结果作为持久快照，当前共 4 份。**读取顺序为 Caffeine → Redis → MySQL 快照，命中即返回并按需回填上层缓存；用户请求不现场聚合点评。快照独立于现有餐厅累计评分统计表，不累计保留历史版本。

## 当前数据与约束

- 点评已有口味、性价比、服务、环境及综合分，还有是否推荐、作者和发表时间。页面显示五分制，现有接口及存储使用十分制；后续计算和展示必须明确分制，避免重复换算。
- 同一用户可以再次评价同一餐厅，历史点评保留。累计统计与近期榜单独立；近期聚合已按周期内每用户最新点评计数，按`created_at DESC,id DESC`选代表。点评直接删除，自然回退到周期内剩余记录，不借用周期外代表。
- 当前餐厅点评统计表保存每用户最新有效点评的累计分与人数，写入时增量维护，读取时相除得到均分；单条综合分当前四维各占 25%。它没有近 7/30 天维度，也没有本榜单的 70% / 15% / 10% / 5% 权重和平滑计算，不能直接充当榜单聚合结果。
- 收藏关系有创建时间，但取消收藏会删除关系，不能直接还原完整历史收藏行为；当前没有可作为真实到店量、订单量的业务记录。
- 普通餐厅、食堂和食堂窗口的评分对象及汇总方式不同；本次榜单仅采用普通餐厅的点评，不混用食堂或窗口数据。
- V43快照表、两级读取、计算、自动发布、调度及前端页面已完成。本轮未重启开发后端或手工回填榜单；新版启动后自动生成，首次生成完成前返回准备中。测试夹具只写隔离库，计算本身不写快照或清缓存。
- 榜单已增加由Boot管理版本的Caffeine依赖，采用显式Cache Aside协调器，而非用一个`@Cacheable`替代逐级回填和发布协调；不改变其他模块缓存或认证Redis配置。
- 餐厅目录按用户位置及地图视口筛选，普通餐厅已有GCJ-02坐标；V14已移除餐厅`campus_code`。榜单现已按独立校区中心及半径划分，不继承目录请求筛选，也不新增餐厅校区字段。
- 保持模块化单体：review 模块负责自己的点评聚合，对外提供应用服务；restaurant 模块不得直接读取 review 的 Mapper 或数据表。架构约束见[开发规则](../../AGENTS.md)。

## 评分规则与待定项

### 已确认的四维权重

口味为主、其他分数为辅，采用以下四维权重计算基础分：

| 维度 | 权重 |
| --- | --- |
| 口味 | 70% |
| 性价比 | 15% |
| 服务 | 10% |
| 环境 | 5% |

基础分公式为 `R = 0.70 × 口味 + 0.15 × 性价比 + 0.10 × 服务 + 0.05 × 环境`；周期内按每用户每餐厅最新有效点评计算加权平均分。该权重已经用户确认，是当前产品规则，没有实际用户数据证明最优；首版参数已随算法版本保存，以后如何调整仍待讨论。

四维均使用相同分制。直接对四维赋权可以清楚表达贡献，避免把口味与已经包含口味的现有综合分再次混合而隐藏实际权重。口味略低但其他维度明显更好的餐厅可能获得更高的基础分；这不是只在口味同分时辅助排序的规则。最终排序再使用下文的平滑公式。

点击量、收藏量代表关注程度，并不能直接证明好吃。用户已决定本阶段不纳入收藏；评分、有效点评人数及同分顺序均采用既定点评规则。

### 已确认的平滑排序方式

采用贝叶斯形式的平滑分，兼顾平均分和有效评价人数，周榜、月榜统一 `m = 5`，首版固定 `C = 3.5`，最低上榜人数另设为 3、最低真实口味均分为五分制 4.0。成熟统计基准及封禁账号专项计分已暂缓，不能把 `m` 当作上榜人数要求。

平滑公式为 `W = (n × R + m × C) / (n + m)`：`R` 为上述四维权重计算的有效点评加权平均分，`n` 为与 `R` 相同统计口径下的有效评价人数，`C` 为相同分制、相同四维权重下的公共基准分，`m` 控制小样本被拉向基准的程度。已确认周榜的 `R` 与 `n` 使用近 7 天，月榜使用近 30 天。

当 `n < m` 时公共参考权重更大，`n = m` 时 `W = (R + C) / 2`，`n` 远大于 `m` 时 `W` 接近 `R`。这里应表达为“`W` 接近 `R`”，不能把 `W` 误当作真实均分；新增评价也会改变 `R`，因此人数增加不保证 `W` 必然上升。

成熟基准仍须确定来自什么人群、什么历史区间，以及何时固定；冷启动使用已确认的 `C0 = 3.5`。不能把某店自己的历史口碑当作所有餐厅共享的公共基准。如果另引入本店历史，应单独定义其作用。

结合用户提供的 IMDb 报告，当前规则遵循以下边界：

- `n` 已确认按用户去重，同一用户对同一家餐厅反复点评不重复扩大人数；删除按周期内回退规则处理，封禁账号专项计分暂缓。`m` 是数学上的先验强度，不是真实评价人数，不计入页面人数；最低上榜人数 `minParticipants` 是独立规则。
- 平滑会把高于基准的分数向下拉、低于基准的分数向上拉，并非一律扣分。例如使用已确认的冷启动 `C = 3.5` 和 `m = 5`，1 人平均 3 分会得到约 3.42 的排序分；它不是餐厅的真实均分。
- 排序分用于比较不同样本规模的餐厅；页面已确认展示对应周期内平滑推荐分和有效评价人数，主分采用对应周期平滑分W，保留一位小数。没有有效点评时，不把基准分伪装成用户评分。
- 同一人数、同一均分的餐厅会得到相同排序分，即使评分分歧不同。该公式不构成置信区间，也不能识别多账号操纵；初期不由此引入未经确认的用户等级票权或异常处置流程。
- 首版使用固定配置基准；后续如改用真实数据，需区分按所有有效计分记录求平均与先求各店均分再平均。较长历史范围及聚合方式均作为暂缓候选，模拟数据不作为生产统计基准。
- 权重、`C`、`m`、统计截止时刻及算法版本应与同一批榜单绑定，避免参数在读取或生成途中变化导致混用；已选用快照表的 `rules_snapshot` JSON 保存，完整规则随计算结果经四榜事务发布入库。

### 已确认的平滑强度 m

周榜、月榜首期统一使用 `m = 5`。统一初值保持规则容易理解；以后是否分榜调整，依据实际近期人数分布与排序案例评估。

以下仅为计算演示：固定五分制 `C = 3.5`、餐厅真实加权平均分 `R = 4.5`，按已确认的同一用户对同一家餐厅只贡献一份理解有效人数。

| 有效评价人数 n | m = 5 的排序分 W |
| --- | --- |
| 1 | 3.67 |
| 5 | 4.00 |
| 20 | 4.30 |

`m = 5` 时，有 5 名有效计分用户，真实均分和公共基准各占一半。校园项目上线初期的近期评价可能不多，这是选择较弱初始收缩的业务假设，尚无真实人数分布证明该值最优。较大的 `m` 更保守，也可能延缓新店体现真实口碑。

`m = 5` 控制平滑强度，最低上榜人数已另行确认为 3、最低真实口味均分为五分制 4.0。这些演示不构成性能或真实使用效果验证。

### 已确认采用近期口碑

周榜使用近 7 天、月榜使用近 30 天范围内的有效评分和人数。该口径更能反映近期口味变化，代价是近期样本可能偏少；对应周期内有效计分用户不足 3 位的餐厅不上榜。

一家店即使历史有 1000 名计分用户，近周只有 1 名，其周榜的 `n` 也应按近周口径确定，不能直接使用累计人数。公共基准可以来自另行确认的更长时间范围，不能把公共先验和该店近期有效样本混为一谈。

### 已确认的最低上榜人数

首期周榜、月榜统一要求对应周期内至少 3 位有效计分用户，即 `minParticipants = 3`。人数沿用已确认的每用户每餐厅一份贡献口径；满足人数条件后，再按平滑排序分排名，同时满足口味及餐厅资格条件。

- 将最低人数设为 3，是在初期参与人数有限与减少单人评分影响之间的产品取舍，没有实际用户数据证明其最优。`m = 5` 继续控制平滑强度，与这项上榜门槛独立。
- 符合条件的餐厅不足展示条数时，允许少展示或空榜，不用零评价或人数不足的餐厅补齐。删除回退或点评过期后人数不足，在重新计算该榜单时退出；默认每轮完成后等待1小时刷新。
- 周/月分别判断。例如近 7 天有 2 位、近 30 天有 5 位有效计分用户，则不满足周榜人数条件，但满足月榜人数条件。

### 已确认的最低评分

在至少 3 位有效计分用户之外，要求对应周期内真实口味均分不低于五分制 4.0。使用与 `R`、`n` 相同的有效点评计算口味均分；四维加权及贝叶斯平滑继续决定符合资格餐厅的排序。

该门槛用于体现“找到真正好吃的餐厅”的目标，避免低口味分餐厅仅因满足人数条件进入榜单。4.0 是已确认的产品规则，没有真实评分分布证明其最优。判断使用统一分制的未舍入均值，展示时再舍入；不把加权均分 `R` 或平滑分 `W` 当作口味均分。删除或点评过期后口味均分低于门槛，在重新计算榜单时退出；默认每轮完成后等待1小时刷新。

### 已确认的上榜对象

仅普通餐厅参与周榜和月榜，食堂整体及食堂窗口均不参与。用户考虑食堂数量较少，本次不增加食堂榜或窗口榜，也不把食堂、窗口的汇总评分混入普通餐厅榜。

### 已确认的排序及同分规则

先按平滑排序分 `W` 降序；`W` 相同时按对应周期内有效评价人数 `n` 降序；仍相同时按餐厅 ID 升序，形成稳定顺序。

同分时优先更多用户的评价结果，最后用固定 ID 避免相同数据在刷新时任意换位。比较使用计算结果，不把页面显示一位小数后相同当成真正同分；W按精确分子、分母交叉相乘比较，Redis完整保存已排序数组。这套规则不增加新的评分权重。

### 已确认的页面展示

首页增加榜单入口，进入独立榜单页选择清水河或沙河校区、切换近 7 天周榜及近 30 天月榜，各展示前 20 名、不分页；不足 20 家时遵循已确认的少展示或空榜规则。已按用户确认图稿实现，名称为“近期推荐榜”。

- 每项显示排名、餐厅封面、名称、对应周期内平滑推荐分和有效评价人数，点击进入现有餐厅详情页。
- 用户看到的分数为五分制口味均分，明确对应近 7 天或近 30 天；平滑分 `W` 用于排名并以“近期推荐分”展示，不作为原始均分。其他页面的累计评分保持各自口径。

榜单按校区划分。每个校区配置固定中心点和覆盖半径，按本站餐厅坐标自动判断是否位于该范围内；用户选择校区后，查看该校区周榜或月榜，各展示前 20 名。

- 初期清水河、沙河各覆盖5公里；用户确认沿用项目参考点，不重新测绘校园几何中心。GCJ-02配置：清水河纬度`30.754400`、经度`103.931200`，沙河纬度`30.675789`、经度`104.099671`，`app.ranking.qingshuihe/shahe`下各设`latitude`、`longitude`、`radius-meters=5000`，不影响目录或地图配置。
- 清水河沿用原站及目录历史参考点；沙河沿用历史导入OSM relation19816230参考点WGS84纬度`30.6781776`、经度`104.0971288`，使用已有导入工具同款`eviltransform.wgs2gcj`转换并保留六位小数。它们是用户选用的范围参考点，不声称为重新测绘的精确中心。转换逻辑复用[历史导入工具](../../backend/tools/import_osm_restaurants.py)。
- 范围表示校区周边的直线距离覆盖，不限定餐厅必须在校园内；不是步行或导航路程。
- 按餐厅共享全部符合资格用户的评价，不按点评者所属校区拆分。一个餐厅若同时位于两个校区的覆盖范围，可进入两个校区的候选集合；账号不因此自动获得校区归属。
- 固定范围便于同校区用户看到一致榜单，不随地图拖动或用户临时位置改变；已选择按位置自动划分，不要求逐家人工指定校区。
- 以到校区中心的直线距离不超过 5000 米判断，包含边界；缺少有效坐标或位于覆盖范围外的餐厅不进入该校区榜。默认校区及选择记忆在页面设计时细化。
- 必须先在每个校区的完整候选范围内应用门槛及排序，再取前 20；不能先取本站前 20，再过滤后宣称得到准确的校区前 20。

缓存结果需区分校区及周期，具体结构留待技术设计；首版周榜、月榜均使用五分制固定参考值 `C = 3.5`，真实统计基准的地区范围及切换暂缓。

### 已确认的更新频率与待定失败策略

每小时后台生成一次各校区周榜、月榜，间隔保持可配置；完整生成成功后发布新结果，用户读取已发布缓存。该间隔是已确认的时效取舍，实际聚合成本仍需实施后验证。

- 新点评、删除后的回退及其他评分变化在下一轮成功生成后反映到榜单，不随用户每次访问重算。正常更新等待取决于调度间隔及生成耗时，失败时的沿用上限见下文已确认参数。
- 该延迟仅针对榜单；点评发表、餐厅详情及现有 ES 同步继续按各自流程更新，不等待榜单调度。
- 即使没有新点评，也要定时处理点评退出近 7 天或近 30 天周期后的评分、人数与资格变化。
- 用户决定暂缓商户快速下榜专项机制，首版生成时按现有商户可见性判断筛选，刷新前可能仍有旧榜单条目；现有详情可见性校验继续适用。刷新失败时保留最近成功结果，并遵守下文已确认的数据年龄上限。

### 首版固定 C 与后续更换

用户已决定首版周榜、月榜均使用固定参考值 `C = 3.5`（五分制），先积累真实数据，后续再讨论统计基准及切换条件。暂不接入自动计算与切换，不以成熟基准规则未定阻止首版实现。

固定参考值是产品假设，不宣称来自真实用户统计，也不展示成餐厅真实均分。没有符合人数及口味门槛的真实点评时，榜单允许为空，不给无评价餐厅制造评分或名次。

后续候选仍可考虑较长历史范围内的真实有效点评、按每用户每餐厅去重后求四维加权均分。此前讨论的近 90 天、每日刷新、按校区分别计算或共享，以及最少记录、账号及店铺覆盖数，均未确认且本阶段暂缓；模拟数据不得用作生产统计基准。

### 时间、重复评价和删除

- 已确认按过去 7×24、30×24 小时滚动统计，每轮生成固定同一个截止时刻 `T`。实现采用左闭右开区间 `[T - 168小时, T)`、`[T - 720小时, T)`；计算使用Instant，T截断至MySQL支持的微秒精度。
- 已确认按“用户＋普通餐厅”去重，周期内只计最新未删除点评；实现按 `created_at DESC,id DESC` 确定先后顺序。食堂及窗口点评不进入统计。
- 已确认删除最新点评后回退到周期内上一条未删除点评；没有剩余点评则移除贡献。两榜分别判断，旧点评可能已退出近周，但仍留在近月内。
- 即使没有新写入，点评也会随时间离开滚动周期，因此只依靠点评事件更新无法保证榜单正确。
- 用户决定暂缓封禁账号专项计分规则，首版沿用既有点评有效性判断及已确认的去重规则。同账号去重无法证明真实到店，也无法完全阻止多账号刷分，不把这类专项治理作为当前首版前置事项。

当前去重规则及待定边界如下，不改变现有点评发表与历史展示功能：

1. 已确认：周榜、月榜各自在自己的统计区间内选取未删除点评，按“用户＋餐厅”分组，每组只计最新一条；实现排序字段为 `created_at DESC, id DESC`。
2. 已确认：每组对分数贡献一份，对人数 `n` 贡献一人。历史点评条数、回复和点赞不增加这个人数；`R` 与 `n` 必须基于同一批入选记录。
3. 已确认：删除入选点评后，回退到同一周期内该用户更早的未删除点评；周期外记录不进入当前榜单，没有剩余记录时移除贡献，同时重新计算人数 `n` 和均分 `R`。
4. 两榜按已确认周期独立计算：用户在近 7 天没有点评、但近 30 天有点评，可以在月榜贡献一份，而在周榜不贡献。

例子：同一周期内，甲先给加权分 3.0，后给 5.0，乙给 4.0。按已确认规则计 2 人、平均分 `R = 4.5`。甲删除 5.0 后，且 3.0 仍在周期内，则回退后为 2 人、`R = 3.5`；如果该旧点评已在周期外，则只剩乙的一份贡献，计 1 人、`R = 4.0`。这只是口径演示，变化在下一轮成功生成榜单后生效。

## 技术选型与待定细节

Caffeine＋Redis两级缓存、MySQL持久快照、近期计算、自动事务发布及小时调度已落地。生成编排不包外层事务，完整计算成功后才发布，单实例并发生成直接跳过，不排队积累。

### 已确认的分阶段实施与测量

用户要求暂缓聚合性能优化，先以最简单方式推进，并分别量化缓存收益：

1. **MySQL直读（已完成）**：联合主键读取快照，不现场聚合或逐店补查；接口见[近期餐厅榜单读取](../api/discovery.md#rankings)，证据见[读取报告](../history/restaurant-ranking-read-2026-11-11.md)。
2. **Redis（已完成）**：Cache Aside及年龄、故障边界，实测耗时差与MySQL查询减少量。
3. **Caffeine（已完成）**：增加本机层并量化三模式收益，证据见[Caffeine报告](../history/restaurant-ranking-caffeine-2026-11-11.md)。

前三阶段已分别交付；统一公开响应与合成快照规模，报告服务/HTTP耗时、分位数、错误及实际调用数。不能拿不同运行的结果直接推断收益，也不能把本机结果称为线上容量。计算与自动生成已验证正确性，尚未做大数据生成压测；聚合成本独立于读取缓存收益。

### 已实现的计算与自动生成流程

1. `RestaurantRankingCalculationService.calculate(T)`在独立RR只读事务内读取一次完整候选、调用review公开服务分别聚合168/720小时，共三条SELECT；不查累计评分表、不请求ES/OSS、不写快照或清缓存、不持有缓存锁。事务超时60秒、单条SQL超时30秒，不增加索引或增量聚合体系。
2. review仅访问自己的点评表，窗口函数先按周期筛选，再按餐厅/用户取`created_at DESC,id DESC`首条，最后聚合人数与四维十分制和；不能先过滤低评分或取全历史代表。restaurant筛选未删除、营业、已确认有效坐标的普通餐厅，封面仅取同店已通过来源的正式首图。
3. 三次读取共享同一RR数据库视图及固定T，避免并发删除导致周月混用状态；RR不冻结业务写入。T限定创建时间，并不重建过去时点已删除记录，也不证明某条T之前创建的记录当时已经提交。
4. Java将四维和除2一次转五分制。人数至少3、原始口味和/人数至少4.0后按W排序；比较W使用精确分子分母交叉相乘，同分再按人数降序和数值ID升序。完整候选按校区过滤、全量排序后取20，不先取全站Top20。
5. 生成四份可被现有读取器接受的结果，连续名次、同轮截止及生成时间，规则JSON保存实际参数；内部保存五分制四维和及W分子/分母，均值和诊断W保留16位HALF_UP，公开口味一位小数仍由读取器处理。无合格餐厅是计算成功空榜，查询/配置/计算异常整轮抛出，不返回半轮成功。
6. `RestaurantRankingGenerationService.generate()`不包外层事务，经Spring代理计算成功并结束只读事务后，调用四榜短事务发布，提交后失效两级；任何计算失败均不调用发布。AtomicBoolean从计算前保护到发布结束，其他并发生成请求立即跳过，finally释放；不占用缓存锁计算。用户请求只读取快照，不现场扫描点评。
7. `RestaurantRankingGenerationJob`在ApplicationReadyEvent后异步首轮生成，独立单线程调度器以fixed delay在每轮完成后等待`app.ranking.refresh-interval=1h`再运行；异常记录类型，旧榜及时间不变，下轮继续。重复就绪事件不重复注册，关闭时取消未来轮次并最多等待70秒让当前轮完成，再尝试中断。不开额外全局TaskScheduler，不改变ES/文件清理调度。
8. `app.ranking.generation-enabled=true`默认开启，关闭后仍可读取已有快照；配置变更重启生效，测试profile默认关闭以保护读取基准与其他模块。暂不提供HTTP手动重算、立即故障重试或分布式调度。

### 存储与计算选择

| 选择 | 适用情况与取舍 | 当前倾向 |
| --- | --- | --- |
| MySQL聚合与应用内计算 | 窗口内逐用户去重后聚合，Java按精确分数比较；生成成本后续再量化 | 已实现首版计算 |
| ES 聚合 | 需要额外的点评检索投影及其同步语义；当前餐厅索引缺少周期内逐用户点评数据 | 不因已有 ES 就默认采用 |
| Caffeine 本机缓存 | JVM 内保存已解析的完整榜单对象，命中后直接返回；需要容量上限、过期及本机版本协调 | 已确认作为一级缓存 |
| Redis String + JSON | 适合每榜前 20 名、无分页、每小时整批生成；保存完整排名与资料，向本机缓存回填 | 已确认作为二级缓存 |
| Redis Sorted Set + Hash | 适合长榜分页、查单店名次、频繁局部更新；需额外维护展示资料和多字段同分顺序 | 首期不采用 |
| MySQL 最近成功快照 | 每个校区、周期保留一份最近成功结果，后续作为缓存未命中或 Redis 故障时的回源 | 表及直读已实现，不作为第三层缓存计数 |

已确认两个校区各提供周榜、月榜，共4份榜单，每份最多20家，两级缓存已接通。统计截止时间、生成时间及规则参数用于判断新鲜度和追溯；已接通自动生成。新增地区、分类或距离组合会增加预生成数量，需另行评估；每个范围仍须先完整筛选排序，再取前20。

V43 已新增 restaurant 模块的 `restaurant_ranking_snapshots`，本地开发库已完成建表，本轮未手工回填；新版启动后自动保存结果。一行保存一个“校区＋周期”的最近成功榜单，7 个字段及全部主键、类型、默认值、CHECK 定义统一见[表结构](../architecture/mysql-schema.md#restaurant-ranking-snapshots)，不在本计划重复维护。

当前计算器与读取器均采用格式 v1：`rules_snapshot` 含整数 `formatVersion=1`、`scoreScale=5`；`items` 每项公开投影为 `rank`、字符串 `restaurantId`、`name`、可空 `coverUrl`、五分制 `tasteScore` 及整数 `participantCount`，详情见[近期餐厅榜单读取](../api/discovery.md#rankings)。计算器同时返回下列内部证据，不透传给用户；结果由生成入口完整计算成功后自动发布入库。

- `rules_snapshot` 保存算法及格式版本、源和目标分制、权重、`C`、`m`、门槛、条数、时间及排序边界、舍入方式，以及实际校区中心、GCJ-02坐标系和半径。回源旧快照时不拿当前配置重新解释旧排名。
- `items` 保存完整展示资料，另含五分制四维精确分数和 `scoreSums`、16位诊断分 `sortingScore`、真正排序所用的精确分子 `sortingScoreNumerator` 与分母 `sortingScoreDenominator`。口味均值内部保留16位，公开读取再舍入一位；不保存点评正文或逐用户名单。
- 建议榜单快照统一使用五分制，生成时将现有点评的十分制原始分数准确换算一次；分制随规则保存。榜单使用独立内部 DTO 和公开 VO，避免复用现有十分制接口模型导致再次换算；公开响应只输出用户需要的字段。
- 封面保存现有正式相册照片标识及本站稳定图片路径，缺图为 `null`，不把会过期的 OSS 签名 URL 写入持久快照。封面和名称允许随小时快照更新，图片读取仍执行原有可见性校验。
- Redis 中的完整 JSON 由本行元数据与榜单数组组成，Caffeine 保存其不可变解析对象；数据库、Redis 和本机缓存读取同一份已生成结果。SQL 不对 JSON 内餐厅逐项筛选、排序或分页。

**发布与恢复语义：**

当前内部发布服务已完成事务、失效与回滚边界，接受已计算快照；已接自动生成入口，没有HTTP写入接口。

- 发布服务要求完整四榜、同一统计截止时刻，在同一短事务内写入四行，任何持久化失败全部回滚并保留两级旧缓存；实际提交后先清Caffeine，再删Redis。拒绝较早截止时刻覆盖较新快照，不增加批次表。用户单次请求只读取一份榜单，不承诺多个请求跨榜单读取的原子切换；与发布重叠的在途本机热读可返回旧结果。生成入口已保证计算失败不调用发布。
- 首次尚无成功结果时不预插空榜行；没有行表示尚无成功快照，`items = []` 表示已经成功计算且没有合格餐厅。生成失败不覆盖旧行，也不更新其时间，失败记录由日志及后续指标承担，不向成功快照表写失败状态。
- 建议不增加独立数据版本、自增批次 ID、`created_at`、`updated_at`、过期时间列或历史明细表。当前单实例缓存发布由全局缓存锁协调，生成入口以AtomicBoolean防重叠；`window_end_at` 判断数据年龄，`generated_at` 标识本次生成；算法及格式版本在规则 JSON 中记录，不作为并发锁版本。
- 超过已确认的 24 小时数据年龄上限后停止展示，保留持久行用于恢复判断，不因缓存过期删除 MySQL 快照。回填不重置窗口或生成时刻。
- 当前按“整榜读取、最多 20 项、只保留最新”选用 JSON；若以后需要历史名次趋势、数据库逐店查榜或长榜分页，再评估快照主表与明细表，而不是先为当前四份小榜单增加关联维护。

已新增Flyway V43及真实MySQL结构测试，结论及本地升级记录见[开发记录](../development.md)。两级缓存已用真实MySQL/Redis验证实际提交后失效、四行回滚保旧、冷加载与发布交错、删除失败绕过及恢复，见[Caffeine阶段报告](../history/restaurant-ranking-caffeine-2026-11-11.md)；生成失败不发布及恢复已由真实MySQL生成专项验证，见[开发记录](../development.md)。

### 两级缓存读写与一致性

以下两级Cache Aside、单实例共用一把全局本地锁及过期、失效与Redis恢复已实现：

1. 键仅由合法校区及周/月周期组成。Caffeine保存不可变展示投影、统计区间及生成时间，Redis保存完整快照JSON；两级展示同一份结果。每次返回独立VO及条目，防止调用者修改共享对象；本机命中不再次解析JSON。
2. Spring单例协调器持有固定的`ReentrantLock`，所有下层加载、回填及发布共用该对象。Caffeine热命中直接返回；未命中加锁后复查本机，再读Redis及必要时MySQL，锁内回填。不同榜单下层加载串行，Redis命中也持锁，Caffeine命中不持锁。Redis阶段8并发延迟增加的历史结果见原报告，当前三模式对照另见Caffeine报告，不把不同时期数字直接相除。
3. Caffeine使用`expireAfterWrite`，默认30分钟、容量最多4条，访问不续期；另保存原写入时刻与有效期检查业务年龄和5秒准备中短缓存。下一次未命中只加载下层已有结果，不重新计算点评；新快照实际提交后及时失效两级，不等自然过期。准备中从Redis向本机回填沿用原过期时刻，不能再延长5秒。
4. 发布和加载共用前述全局缓存锁：聚合与计算放在锁外，同一实例的生成任务自身串行；发布时获取全局缓存锁，写入并实际提交快照，再删除对应 Redis 与 Caffeine 条目，最后解锁。锁必须覆盖事务实际提交，不能在 `@Transactional` 方法体内提前释放、让外层事务随后才提交。加载需读取最新已提交快照，不携带跨越发布过程的旧长事务。
5. 首期按现有单实例运行。本地锁与删除本机缓存只作用于当前 JVM；以后多实例的其他 Caffeine 仍可能额外滞后约一个本机有效期及加载耗时，需重新设计发布协调及本机失效通知，不能直接将本地锁方案当作多实例保证。
6. 共锁合并同一实例的并发冷加载，已验证两级开启时16请求仅一次Redis GET及一次MySQL回源；正常空榜按正常TTL缓存，无快照PREPARING短缓存最多5秒。`tryLock`默认最多等待1秒，超时/中断安全返回503且保留中断状态，`finally`释放锁。专用Redis连接及命令超时各200毫秒，复用服务器、认证、DB及Netty线程资源，不改共享登录Redis工厂。
7. 本机过期、Redis过期和业务允许陈旧时间分别配置。三层每次读取均检查数据年龄；Redis TTL取2小时与剩余可用时间中的较小值，GET不续期，SET与PX原子执行。本机物理缓存即使尚未到期也拒绝超龄结果。GET/SET故障标记四键绕过并清对应本机结果，回源最新MySQL；故障不是成功空榜。
8. 提交后先清Caffeine；DEL失败标记对应键绕过Redis，从MySQL读取最新已提交快照，恢复前不回填Redis，但可把最新MySQL结果缓存于本机。修复只DEL固定键，每5秒至多尝试一次、3次失败后冷却1分钟再开下一轮，不在锁内睡眠。启动本机为空、Redis四键默认待清理；就绪事件和首次下层读取均有门禁，清理成功才恢复Redis。重试不携带旧结果回填，崩溃残留由下次启动清理、TTL与最大年龄共同兜底。

当前仅4个合法榜单键，本机最多4条；Caffeine在现有JVM内运行，不新增独立服务。已量化合成数据热读取成本，实际命中率、内存收益与线上容量尚未测量。

### 一致性风险与处理建议

计划每小时生成，读取允许一定延迟；按最终一致设计，MySQL最近成功快照为权威来源。不承诺MySQL、Redis与Caffeine同时切换，也不承诺点评后立即改变排名。当前两级读取、内部计算、事务发布及Redis恢复已实现，计算后自动发布和调度也已完成。

| 场景 | 风险及建议 |
| --- | --- |
| 仅重建线程加锁，发布线程不使用同一把锁 | 旧加载仍可在新快照提交、删缓存后回填旧结果；发布和加载必须使用同一把全局缓存锁，覆盖实际提交、失效以及读取回填全过程 |
| MySQL 已提交 v2，但 Redis 删除失败仍为 v1 | 本机过期后直接读 Redis 会退回旧榜；失败后清理本机旧结果，标记绕过落后 Redis，从最新快照加载，并重试失效 |
| 进程在快照提交后、删除 Redis 前崩溃 | 锁和本机绕过标记一起丢失，Redis 仍可能保留旧结果；启动时校验或清理缓存，Redis 有效期与快照最大年龄兜底，不能用进程内互斥宣称跨故障原子性 |
| 后续多实例运行 | 删除当前实例 Caffeine 不会删除其他实例本机结果；仅靠 30 分钟过期时，其他实例可能额外显示旧榜约 30 分钟及加载耗时，需要重新设计协调及失效通知 |
| 商户删除、停业后只清缓存 | 读取旧 MySQL 快照可能重新带回商户；如要求立即下榜，需更新快照、维护屏蔽信息或读取时校验资格，不能把清空两级缓存当成完整处理；具体业务要求与实现仍待定 |
| 连续刷新失败、旧快照反复回填 | 新的缓存写入时间不能代表数据已更新；各层按统计截止时刻判断数据年龄，最大沿用时间及过期响应见下文已确认规则 |

首期启动生成与小时调度已共用同一实例内生成入口，防止生成任务重叠；缓存加载与快照发布共用一把全局本地锁，生成入口的防重叠不通过长时间持有缓存锁实现。在所有读写入口受控、快照实际提交及失效成功的条件下，该方式可防止进程内旧加载回填，不要求先实现多实例版本 CAS 体系。快照版本仍可用于追溯、较早统计边界校验和恢复判断；事务边界、删除失败、进程崩溃及多实例问题需要分别验证，不能仅靠“重建只允许一个线程”推定已经解决。

### 已确认的持久快照与待定恢复细节

MySQL 仅保留每个“校区＋周期”最近一次成功生成的完整榜单快照，当前共 4 份；两级缓存保存这些已生成结果，不累计保存所有历史版本。快照属于独立榜单结果，不覆盖现有餐厅累计点评统计表。

- 缓存无可用结果或Redis不可用时，读取最近成功快照；用户请求不现场聚合点评。Redis失效或回填失败不撤销已保存快照，绕过与重试已落实；Caffeine与Redis共用同一发布及失效边界。
- 刷新失败保留最近成功结果，并记录统计截止时刻、生成时间及失败情况；沿用上限及过期响应见下文已确认规则，存储均不可用时的响应细节另定，不无限期展示旧榜。
- 已实现启动策略：服务就绪后异步生成，每轮结束等待1小时再刷新。尚无成功快照时显示“榜单准备中”，生成完成但没有合格餐厅时显示正常空榜；不能把生成失败伪装成无人评价。

### 已确认的过期与故障沿用参数

自动生成已接通，默认每轮结束等待1小时再刷新。Caffeine本机30分钟写后过期、三层读取`app.ranking.max-snapshot-age`（默认24小时）及Redis TTL约束均已落实：

| 参数 | 已确认值 | 含义 |
| --- | --- | --- |
| Caffeine有效期 | 写入后30分钟 | 本机热读不续期，提交后主动失效；准备中最长5秒，超龄结果立即拒绝 |
| Redis 有效期 | 写入后 2 小时 | 正常更新仍由新快照提交后主动失效；缓存自然过期时只重新加载快照，不触发点评聚合，也不等到 2 小时才展示新榜单 |
| 快照允许的数据年龄 | 最多 24 小时 | 刷新失败时允许继续展示范围内的最近成功结果；超过上限的新读取返回“榜单暂时不可用”，保留持久快照用于恢复判断，正常空榜与不可用分开 |

24小时是生成失败时的容忍上限，正常每轮完成后等待1小时再更新。数据年龄从统计截止时刻计算，生成耗时、跨层回填及重启均不重置；三层读取在刚好24小时时仍可用，超过后不返回旧条目。Redis回填TTL不超过剩余可用时间，本机逐次检查业务年龄；刚好边界时可返回但不新回填。

Redis阶段运行参数统一位于`app.ranking`：`redis-enabled=true`（此开关只控制榜单Redis）、`redis-key-prefix=ginkgo:restaurant-rankings:v1:`、`redis-ttl=2h`、`preparing-ttl=5s`、`lock-wait=1s`、`redis-command-timeout=200ms`、`redis-connect-timeout=200ms`、`repair-delay=5s`、`repair-attempts=3`、`repair-cooldown=1m`。键后缀为`{campusCode}:{periodType}`，固定四键，不支持请求自定义。关闭榜单Redis仍使用相同MySQL校验投影，便于分阶段对照；不会关闭认证Redis。

Caffeine阶段增加`app.ranking.caffeine-enabled=true`、`caffeine-ttl=30m`。仅关闭本机缓存可复跑Redis模式；两开关均关闭为MySQL基线，均使用同一公开投影。只关闭榜单Redis仍允许Caffeine→MySQL，提交后仍清本机缓存；不提供客户端切换来源的参数。

- [IMDb Ratings FAQ](https://help.imdb.com/article/imdb/track-movies-tv/ratings-faq/G67Y87TFYYP6TWAV)及[普通条目加权评分说明](https://help.imdb.com/article/imdb/track-movies-tv/weighted-average-ratings/GWT2DSBYVT2F25SK)：链接来自上述报告，本轮未重新核验在线页面。报告记录的 Top 250 门槛与示例参数不能直接作为校园项目规则，也不能把公开榜单公式称作 IMDb 全站评分的完整实现。
- [Google Maps 热门时段](https://support.google.com/business/answer/6263531?hl=en)：来自匿名汇总的到访数据，并相对本店高峰展示，不能直接套用为本项目的跨店美味排名。
- [Google 本地排名](https://support.google.com/business/answer/7091?hl=en)：相关性、距离和知名度共同作用；属于搜索排名，没有公开可照搬的周榜评分公式。
- [Yelp Top 100 2025](https://www.yelp.com/article/top-100-us-restaurants-2025)：结合评价分数、数量等信号及人工整理，支持“质量与评价规模共同考虑”的方向，不提供本项目可直接采用的权重。
- [Discourse Hot 说明](https://meta.discourse.org/t/296747)、[Hot 源码](https://github.com/discourse/discourse/blob/main/app/models/topic_hot_score.rb)及[Top 源码](https://github.com/discourse/discourse/blob/main/app/models/top_topic.rb)：热度衰减和周期榜是不同产品；论坛的帖子创建时间限制不能照搬成餐厅创建时间门槛。
- [Hacker News 官方说明](https://news.ycombinator.com/newsfaq.html)：讨论投票与时间共同影响排序，还包含反滥用规则；餐厅场景若引入衰减，应考虑点评或活动时间，不能按餐厅创建时间惩罚老店。

这些来源用于辨明“人气”“近期热度”“质量口碑”的差别，没有公开统一的餐厅热门算法，也不能据此承诺榜单一定代表真实口味质量。
