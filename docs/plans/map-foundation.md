# 高德地图基础闭环开发计划

规划日期：2026-10-31。状态：已实现真实范围查询、独立前端map模块、SDK加载适配和移动结束后300毫秒自动查询；接口/状态与SDK替身浏览器验收通过。本地Key和Vite安全代理已配置，真实底图及缩放自动查询已验证；生产代理和手机唤起待验收。已按用户要求改为只传目的地的高德跳转入口及独立示意预览；站内不选择起点，线上和真机验收明确暂跳过；当前状态详见[开发日志](../development.md)。地图服务采用高德JS API 2.0，前往餐厅采用高德URI地点跳转，由高德处理定位和路线；产品使用规则及当前可用能力见[功能说明](../features.md)。

## 交付目标与范围

完成“筛选本站餐厅 → 地图选店 → 阅读已有餐厅详情/点评 → 在高德中打开”的闭环。地图、导航均允许访客使用，已有写入权限保持不变。

- 在已有/map入口实现真实地图；电脑左列表右地图，手机地图加底部可展开结果面板，保留既有主导航及底部导航。
- 目录和地图共享关键词、分类、排序、隐藏停业、人均上限、距校区直线距离上限。无关键词时地图应用已确认视口；有关键词时本站目录跨视口查询，另行搜索高德餐饮地点，分类/消费等只作用于本站结果。地图明确当前页点位范围，移动不重搜关键词；清空后恢复视口浏览。
- 点位和卡片显示真实评分、人均、经营状态及选中状态；卡片打开现有/restaurants/:id详情，已有点评功能直接复用。
- 第一版包含本站位置浏览、有限点位聚合及外部步行导航。2026-10-31补充交付高德基础地点关键词搜索，优先成都但不锁城，与本站分组、独立分页，谨慎匹配并复用本站详情；不自动入库。用户明确暂缓学生提交，提交收录和手动添加只保留禁用占位，地图选点、审核、站内路线预览仍为后续交付，不把MAP-02的完整新增流程视为已实现。本人单次定位已交付：主动点击、浏览器授权、WGS84转换GCJ-02、独立蓝点；仅内存、不绑定邮箱保存。尚无连续跟踪、距我排序或半径筛选，生产HTTPS定位待验收。
- 保留MySQL作为业务数据源；第一版不引入ES、Redis GEO、消息队列或新地理服务。复用坐标、统计和筛选字段，预计无需Flyway迁移；若核验发现确需结构调整，另行说明。

## 当前基础与配置前置

已有/map占位页、餐厅目录和详情接口、GCJ02坐标及needsLocation标记；校区参考点沿用30.7544/103.9312。餐厅列表为分页接口，不能将其当前页当作地图全量数据。历史日志中的店铺/坐标数量不作为当前数据验收结果，开发开始时重新只读核验。

1. 核对高德个人认证、实际用途许可、地图初始化及地点搜索配额、域名白名单；开发和生产分别配置。已交付的PlaceSearch插件复用JS API Key，不额外要求Web服务Key。
2. JS API Key属于浏览器可见标识但仍通过环境配置提供、不入库入Git；生产安全密钥留在服务器，采用官方安全代理方案。代理限制固定上游和必要路径，不建立任意URL转发入口，不在日志中输出凭据。
3. 地图SDK按/map页面懒加载；无Key、加载失败、配额限制时提供具体提示和目录入口，其他页面不依赖SDK成功。
4. 当前线上HTTP不能作为手机浏览器本人定位的可靠验收环境。基础版不要求本站定位；HTTPS、证书和域名配置纳入后续定位前置，不因缺少定位阻断地图阅读及外部导航。
5. 开发环境先验证一处已确认真实餐厅的坐标落点；待定位数据保留原状态，不通过批量填入校园坐标制造地图点位。

## 分步实施与审核

每步完成代码、必要测试和文档后单独审核；不自动创建分支。开始实现前如需功能分支，应先说明名称、develop基线和用途并取得同意。

| 步骤 | 具体交付 | 通过条件 |
| --- | --- | --- |
| M0 配置与数据核验 | 只读统计已定位/待定位、确认真实坐标来源；核对Key、域名、配额、安全代理配置方案 | 已知餐厅落点可核实，缺失项明确；不输出密钥、不写业务库 |
| M1 详情导航入口 | 详情提供“在高德中打开”、复制地址；共用导航URL构造与位置有效性规则 | 手机和电脑起点语义明确，特殊店名编码正确，待定位不生成错误导航 |
| M2 地图点位后端 | 新增公开只读视口接口，复用完整筛选条件、真实评分及稳定排序 | 真实MySQL验证范围边界、筛选、计数、上限、删除可见性；不依赖列表分页 |
| M3 SDK与地图选店 | SDK加载/销毁、点位与聚合、回默认/回校区、选中卡片、详情跳转；替换/map占位 | 真实底图和本站点位可用，无凭据/SDK失败可回目录，不产生模拟业务数据 |
| M4 条件与区域联动 | 共享条件、区域确认、结果面板、请求取消/顺序保护及返回状态恢复 | 目录与地图条件不互相覆盖，地图/面板结果集合一致，晚到响应不覆盖新结果 |
| M5 完整验收与发布准备 | 前后端检查、浏览器和手机高德导航、配置/版本检查及文档 | 明确自动测试、替身测试与真实外部导航证据；审核后再提交/推送和部署 |

M1不依赖地图SDK，可以先交付实际导航价值；M2与后续页面接入按上述顺序实施。每步运行与修改相符的验证，不将历史测试成绩记为本轮结果。

## 高德导航规则

- 按用户最终范围，统一使用官方HTTPS地点入口https://uri.amap.com/marker，只传position=经度,纬度、name、coordinate=gaode、src=ginkgo及callnative=1。不传固定校区起点，不开发站内起点选择、路线规划或导航定位。
- 按钮为“在高德中打开”，由高德处理后续定位和路线选择；手机按官方参数尝试唤起App，电脑打开地点页，不把手机空起点导航能力假定为电脑也支持。
- 所有跳转由用户点击触发，不用定时器猜测App是否启动成功。本站“我的位置”仍可用于看附近地图，但不作为外部跳转的前置条件。
- needsLocation=true、缺失/非法坐标、已删除餐厅不允许按坐标导航；提示待确认位置并保留可用地址复制。URL使用标准编码，用户店名不得改变参数或生成任意协议链接。
- 从详情读取当前可见餐厅；地图只携带选中ID进入详情，不把客户端URL传入的坐标当作权威目的地。无站内路线/时间结果时不展示推算步行时长。
- 链接与坐标边界已有本地自动验证；用户明确本轮跳过生产HTTPS/代理及真机高德验收，不将其写成已通过。按当前约定，基础导航交付收尾，其余是未来发布前验收事项。

## 拟定点位接口（未实现）

建议GET /api/restaurants/map-points，归restaurant模块；专用Controller/DTO/VO和只读应用服务访问本模块Mapper。安全配置按具体GET路径公开，不扩大其他接口权限。现有详情{id}路径与固定子路径的匹配加入回归。

| 输入 | 规则 |
| --- | --- |
| west、south、east、north | 必填，经纬度有限值、合法范围，west<east且south<north；首版成都使用场景不支持跨日期变更线，非法400 |
| keyword、category、hideClosed、maxPrice、maxDistanceMeters、sort | 与目录同一规则，保留8种已有排序；距校区上限始终使用原校区参考点，不随视口中心移动 |
| 点位数量 | 服务端固定上限暂定500，不允许客户端无限扩大；限值需通过实际渲染测量核对，不宣称已完成性能优化 |

- 基础条件复用catalog可见性、关键词、标签和统计SQL，增加已确认GCJ02坐标及视口条件；先筛选再排序/截取。地图不恢复已取消的杯型UI或筛选。
- 拟返回points、matchedCount、returnedCount、truncated、limit及bounds。points仅包含ID、名称、坐标、分类、地址、人均、经营状态、评分、人数/条数及校区距离等公开卡片字段，不含作者身份或管理字段。
- matchedCount是该已确认视口内、符合条件且可定位的完整数量；returnedCount是实际返回数量。最多返回500条，用同一只读事务快照查询计数和点位，排序以名称/ID补稳定次序。
- truncated=true时显示“此区域共N家，当前展示500家，请缩小范围”；侧边面板只能标明同一批已展示结果，不把截断结果声称为全部。聚合仅覆盖已返回点位，不能用聚合掩盖服务端截断。
- 待定位店不计入视口matchedCount（位置未知无法归属视口），目录继续保留。区分“此区域无可定位餐厅”和“本站无餐厅”，提供回目录查看入口。
- 新增/编辑/删除后使已有地图快照失效并刷新；同一已提交响应内地图与面板必须一致，不承诺两个独立请求在并发写入时获得全站相同快照。详情对已删除内容保持404并清理选择。

## 前端状态与生命周期

- 复用restaurant目录条件存储，将地图视口、已确认查询区域、selectedRestaurantId和地图加载状态留在地图功能内；不在第二个组件复制一套业务条件。
- 用户已确认自动查询：拖动/缩放结束后等待300毫秒，合并moveend/zoomend并自动查询最终视口，不再要求手动点击“搜索这一区域”。筛选确认立即进入同一防抖查询；失效请求立即取消并作序号保护。选店只更新高亮与卡片，不强制移动地图，因此不制造自动查询循环。
- 地图加载前通过已有API条件读取保持正常；目录与地图切换保留条件，地图→详情→返回保留本次会话中的视角/已提交范围，进入指定餐厅时显式定位该店。首版不引入全站URL条件同步重构。
- 默认遵循需求的成都视野，提供回成都默认范围、回校区；移动端面板不遮挡缩放、品牌版权及底部导航。无评分、停业、选中状态兼顾文字提示，密集点使用MarkerCluster。
- SDK加载使用共享Promise、超时和可控重试；离开页面销毁地图、事件监听和挂起请求；宿主尺寸变化后正确重算布局。API取消加请求序号保护，避免旧筛选/旧视口覆盖新结果。
- API失败、SDK失败、无结果分别呈现；失败保留条件和上次结果但标明未更新，避免旧点位伪装成当前筛选结果。弹层支持Escape、焦点与小屏滚动。

## 验证与可讲述的工程成果

- 后端：真实MySQL隔离库验证bbox边界、组合筛选、无评分、缺坐标/待定位、停业/软删除、500条及超限、稳定排序与精确计数、非法参数；测试数据不写业务库。
- 前端：导航URL及坐标校验、选店/取消、条件保留、区域确认、响应乱序、失败重试、卸载清理、聚合选择与返回状态；SDK替身只验证协议及状态，不称为真实高德接入验收。
- 真实浏览器：1440/390/320px与手机横屏检查布局、面板、焦点、返回恢复和SDK阻断；使用已核实位置检查真实底图/导航，不发布虚构餐厅。Android/iOS能覆盖多少记录多少，未具备设备则明确待验收。
- 记录视口查询数据规模、EXPLAIN、响应时间和点位渲染耗时；隔离样本用于边界和性能测试，明确非真实用户规模。
- 可沉淀的技术主题是视口查询与完整筛选、上限语义、异步请求顺序、坐标边界和第三方失败隔离；ES搜索作为后续独立阶段，避免本轮同时承担多套索引一致性。
- 接口实现后更新api.md；能力实际开放后更新features.md；阶段结果写development.md。计划协议不得提前写成已上线接口。
