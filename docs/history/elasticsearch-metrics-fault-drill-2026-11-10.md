# ES 检索监控故障演练（2026-11-10）

首次演练保留发现问题时的结果；同日后续修复及复测见文末。当前已完成响应超时修复，暂停场景复测通过。

## 首次演练结论

真实停止 ES 后，MySQL 兜底、熔断拒绝、半开探测、恢复及监控采集通过。**暂停 ES 模拟无响应时，请求超过客户端 20 秒等待上限，及时降级未通过。总体不能判定全部通过。** 本轮仅测试和记录，未修改业务实现。

## 环境与方法

Windows 本机后端、MySQL/Redis，Docker Elasticsearch 9.5.4、Prometheus，Windows Grafana 12.2.1。数据库有 9564 家餐厅。只执行列表和指标读取，浏览与关键词 coffee 交替、每页 1 条、串行低负载，不作为生产性能评测。

分别使用容器暂停和停止模拟无响应与连接不可用；脚本通过 finally 恢复 ES，前后核对餐厅数量、投影版本总和、Outbox 状态数量。

## 首次演练的问题与边界

- 当前配置 connect-timeout=2s、socket-timeout=3s，暂停故障却等待超过 20 秒。依赖字节码显示 Spring Data 6.0.8 将 socketTimeout 传给连接配置，但该请求配置路径未显式设置 responseTimeout。这是后续排查线索，尚未修复复测，不能认定根因已确认。
- 20 秒是客户端等待上限，不表示后端永远不超时。后续应优先修复响应超时，并重新验证暂停场景。
- 半开状态短暂，直接轮询未捕获状态 2，通过日志确认转换；30 秒抓取不能保证捕获所有短暂状态。
- 新标签计数器首次采集前的事件不能用 rate/increase 完整还原；本报告次数使用指标快照差核实。Grafana 低流量分位数及速率仅验证展示，不作为精确事件数或性能结论。
- 过程截图可能显示上一抓取周期的打开状态；最终关闭以末尾 Prometheus 状态 0 和实际 ES 查询为准。收尾重新检查 ES 集群 green、容器未暂停，列表返回 ES 且未降级。

## 同日后续：响应超时修复与复测

根因是 Rest5 客户端默认将请求级 responseTimeout 设为 0（无限等待），覆盖了连接层 socketTimeout。原先只配置连接层的3秒等待，无法约束已建立连接后的响应等待。现在通过 Spring Data 的 Rest5 请求配置回调，同时将请求级响应超时设置为既有 socket-timeout，保持默认3秒；没有增加线程超时包装或后台查询重试。不足1毫秒的时长会被拒绝，避免转换成0后意外无限等待。

新增无外部依赖的真实TCP回归测试：接受连接但不返回数据，使用250毫秒配置验证客户端在宽松3秒容差内抛出读取超时；不是仅断言配置值。完整 `mvn verify` 和打包通过：共703项，执行280项、跳过423项，失败/错误0；日志为 `backend/target/es-response-timeout-verify.log`。

后端重新打包启动后，在相同本机环境重新运行暂停 ES 的完整演练：

| 场景 | 修复后实测 |
| --- | --- |

| 暂停无响应 | 10次均HTTP 200并回退MySQL，整体约3.14–3.30秒，超时指标增加，随后熔断打开 |
| 熔断拒绝 | 5次均正常SQL兜底，不增加SDK尝试及ES阶段计时样本 |
| 半开失败 | 直接观察到半开状态，探测超时后SQL兜底成功并重新打开 |
| 恢复ES | 恢复容器后约10.7秒重新使用ES，随后5次均使用ES；最终状态关闭 |
| 采集与数据 | Prometheus采到0→1→0，故障期间后端目标UP；业务数据及Outbox汇总前后相同 |

本次复测共47次读取、109项脚本断言通过，无最终查询失败。原始证据 `D:/eat/.codex-previews/es-response-timeout-fixed-20261110/result.json`，脚本 `D:/eat/.codex-previews/grafana/timeout-fixed-drill.py`。不将首次失败轮或定向复跑数量累加成覆盖数；首次失败证据保留。

该3秒限制针对单次HTTP响应等待，整体接口还包含SQL兜底及可能的多阶段调用，不是接口总时限。收尾确认容器未暂停、ES集群green。复测范围是本机串行故障演练，不代表线上或并发容量保证。
