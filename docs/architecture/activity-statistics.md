# 使用统计存储结构

状态：V49、Redis资源、前后端采集／同步／清理／读取已接入，代码已随首次部署发布到服务器；2026-11-20用户核对依赖并开启服务器环境开关，等待本轮自动发布重启生效。项目默认关闭，由环境显式开启。业务规则及上线步骤见[统计计划](../plans/admin-activity-statistics.md)，现行协议见[使用统计API](../api/statistics.md)，字段与约束见[MySQL结构](mysql-schema.md#activity-statistics)。

## 存储分工

| 存储 | 结构 | 内容 |
| --- | --- | --- |
| MySQL | `activity_daily_summaries` | 每日活跃、新增用户及正式发布点评汇总，一天一行 |
| Redis | 每个统计日期一个Set | 当天主动访问的普通登录用户ID |
| 现有MySQL元数据 | `app_metadata` | 正式启用时刻与非个人采集运行标识 |

存储及接口归statistics模块，注册与点评通过`ActivityContributionService`公开服务注册提交后回调，作者资格通过user公开账号服务确认。Redis不保存新增用户数、点评数或业务计数凭据；MySQL不保存活跃账号明细，也不新增计数凭据表。

## Redis键结构

| 项目 | 定义 |
| --- | --- |
| 键 | `foodmap:activity:users:YYYY-MM-DD`，日期采用`Asia/Shanghai` |
| 类型 | Set |
| 成员 | 用户ID的规范十进制字符串，范围1至9223372036854775807 |
| 到期时间 | 统计日期加90天后的北京时间00:00，转换为Unix秒后使用EXPIREAT |
| Redis连接 | 沿用应用Redis连接及所选逻辑库，键直接带上述前缀，不再次套用Spring缓存前缀 |

不预创建空Set。Redis不保留空集合，键不存在既可能代表无人访问，也可能代表未启用、过期或数据丢失，不能只凭不存在就声称当天活跃为0。

[原子写入脚本](../../backend/src/main/resources/redis/activity-record-user.lua)使用一个键及两个参数：用户ID、固定绝对到期时间。调用方验证身份及普通用户资格，确定服务端日期、启用边界和到期时刻；脚本只负责SADD与EXPIREAT原子执行，不提供HTTP鉴权或客户端自报日期入口。返回1为首次加入、0为已存在、-1为保留期已结束；非法参数报错且不写入。ID始终按字符串处理，不转Lua浮点数，避免大ID失真。

同一统计日期的重复写入始终使用同一个绝对到期时刻，不按最后一次访问延长90天。过去日期的到期集合不得重建。首次启用只记录启用后的行为，不从已有账号、点评或访问日志回补集合。

## 查询与汇总边界

- 今日活跃读取当天Set的SCARD；近7日活跃对今天及前6天的集合做并集并计数，使用SUNION后计算成员数，不把每天人数相加，也不创建持久并集键。第一版沿用单Redis实例。
- Redis命令失败、已知集合丢失或采集覆盖无法确认时，不把缺键当作真实0。只有确认该日采集正常且没有有效访问时，才保存0；已知不完整使用PARTIAL，无法确认使用UNKNOWN。
- 活跃人数每轮约60秒同步一次，并在跨日后补存前一天。同步写入绝对人数及本次取数时间`active_synced_at`，不执行累加；仅更新活跃字段，不覆盖并发增加的注册或点评数量。迟到同步不得覆盖更新的同步结果，已知缺失不能仅因下一次读取成功就恢复NORMAL。
- 新增用户和正式点评首次成功创建并提交后，以独立事务更新MySQL对应日期的计数；沿用现有业务首次创建与请求重放边界，不从HTTP请求次数计数。删除点评不回扣，不用现存点评数量重建历史发布量。
- 日汇总没有`updated_at`。页面更新时间由后续接口返回本次成功读取时间，不能与活跃同步时间混用。
- 日汇总按北京时间自然日期保留1个日历年，删除早于当天减1年的行；清理Redis集合不能触发删除或重算仍在保留期内的日汇总。同步不得用已过期的集合覆盖历史人数。

## 启用元数据

键`activity_stats_started_at`使用现有`app_metadata.metadata_value`保存UTC ISO-8601时刻，例如`2026-11-20T07:00:00Z`。不存在表示从未启用，不等同于当天00:00；启用后保持首次值，不随重启、升级或暂停采集而重置。另以`activity_stats_last_seen_at`保存维护任务最近成功时间，以`activity_stats_redis_fingerprint`保存Redis的run_id及evicted_keys；均为statistics拥有的非个人运行元数据，不是计数凭据，不包含账号ID。

V49不插入该键、不创建日汇总行，也不访问Redis。后续正式启用时才写入元数据并初始化当日采集状态。启用首日不足完整自然日时标为PARTIAL；启用前没有汇总行，不能补成0。

## 故障与部署边界

后续采集失败不回滚已成功的注册或点评。核心业务提交与独立统计更新之间存在进程崩溃窗口；当前结构没有持久事件或计数凭据，不能保证自动补回，也不能对结果不明的增量盲目重试。既有发布幂等只防止重复创建业务内容，不等同于统计已可靠提交。

Redis持久化、备份和内存淘汰策略须在部署验收时核对。2026-11-19本地启用前确认Redis已开启AOF、所需命令可用、没有已发生的内存淘汰；运行实例仍沿用192MiB及allkeys-lru，本次未修改实例策略。逻辑库及键前缀不能隔离实例故障。集合丢失后，仅有日汇总无法恢复账号去重，后续重新累计不能当作完整数据，也不能用较小值覆盖此前已保存的人数。不能以MAX覆盖等方式声称已修复缺失，受影响日期和7日窗口须保留不完整状态；本地联通不等于服务器Redis持久化和淘汰策略已验收。

管理端前端不直接访问Redis或MySQL。注册和点评仅在首次业务创建节点注册回调，成功重放提前返回；回调等待整笔事务提交后用REQUIRES_NEW短事务累加，审核后续失败会丢弃回调。普通用户原作者的角色在注册回调时确认，后台审核身份不替代作者；统计不保存增量重试队列，结果不明时只降级日期状态。

## 采集运行约定

- 配置`ACTIVITY_STATISTICS_ENABLED`，默认false。显式开启后，应用就绪启动独立单线程维护任务，首次执行保存启用时间并初始化当天；之后每轮完成60秒后再执行，同步当天及昨天的活跃人数、清理超过1个日历年的汇总。任务不占用ES／OSS调度器，失败不会终止后续周期。关闭后停止采集，历史仍可读，不重置起点。
- 第一版要求单后端采集实例及单Redis实例。应用内协调器串行处理状态、跨日和同步；SQL仅更新所属指标，活跃同步比较时间阻止旧结果覆盖。多后端部署前需增加跨实例采集协调，不能把当前实现当作已支持多实例。
- 统计复用现有Redis服务器、凭证及逻辑库，但使用独立200ms命令／连接超时和连接生命周期，复用既有Netty资源；不改变登录会话和验证码连接配置。Redis需允许SADD、EXPIREAT、TIME、SCARD、SUNION、脚本执行以及INFO server／stats。若运行标识无法读取则保守降级，不能默认认为完整。
- 每次应用重新初始化采集，以上次维护时刻至当前日期标记不完整；维护间隔超过2分钟、时间回拨、已知计数失败也保守降级。期间完全缺失的日期保留NULL，不能从现存账号／点评重算。未知计数继续保持NULL，后续行为不会把它伪装为完整数值。
- Redis运行ID或累计淘汰数改变时，最近90天已有汇总标记为PARTIAL；即使Redis从持久化成功恢复也采用保守处理。每日人数缩水时保留此前确认的人数下界并标记PARTIAL；七日并集小于任何已存日活时不返回较小的正常数，返回NULL／UNKNOWN。七日查询跳过启用前日期。
- 这些检测无法发现所有静默删键：从未同步成功的成员丢失、删除后又增长至相同人数等情况可能无法识别。运维禁止手动删除统计键，需核对持久化、备份和内存淘汰策略；不承诺从汇总恢复去重集合。认证与统计共享Redis实例时，实例故障也会影响既有认证链路。
- 活跃由用户端主动页面访问、登录完成和恢复可见上报，无定时心跳；请求不携带路径、日期或用户ID，换号／隐藏／卸载取消旧请求。网络未送达无法追补，服务端按认证账号去重，但不证明请求一定来自人工操作。
