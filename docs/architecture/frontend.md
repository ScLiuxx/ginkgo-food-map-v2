# 前端架构

本文维护前端分层、模块协作、状态生命周期和关键复用机制。页面外观与当前功能见[功能说明](../features.md)，请求响应见[API文档](../api.md)，阶段改动和浏览器验证见[开发记录](../development.md)。

## 微信小程序端（2026-11-23）

小程序位于 `miniprogram/`，使用微信原生 WXML/WXSS/TypeScript，不引入 uni-app 或 Taro，也不复用 Vue 组件。它与 Web 端共享同一套后端 HTTP 契约，但与 Web 代码完全隔离，单独通过微信开发者工具编译。

```text
miniprogram/
├── app.ts / app.json / app.wxss   启动入口、路由表与全局视觉变量
├── assets/                        TabBar 图标与地图标记
├── custom-tab-bar/                悬浮玻璃底部导航
├── config/                        环境地址与相对图片地址拼接
├── typings/                       当前代码实际使用的微信 API 最小类型声明
├── shared/                        请求层、登录态存储、图片处理与格式化工具
├── modules/                       按业务域划分的接口与展示模型（含地图点位）
└── pages/                         找店、地图、消息、我的、我的内容、登录、店铺详情、写点评、近期推荐榜、新店投稿与资料纠错、公开主页与关注名单
```

- 视觉采用半透明玻璃层、环境色光斑、高光描边和悬浮胶囊导航；页面正文位于环境光之上，玻璃面板在支持 `backdrop-filter` 的环境启用真实模糊，不支持时退回半透明背景与内阴影。原生 TabBar 无法模糊，因此使用 `custom-tab-bar`，四个 Tab 页在 `onShow` 回写选中项。
- 请求层显式区分 `none`、`required`、`auto` 三种认证模式：公开读取不携带令牌，私有请求无令牌时本地拒绝；401 只清理产生该次失败的令牌。
- 登录字段适配后端现有的 `username` 参数，同时接受用户名、注册邮箱和纯数字学号，学号由服务端补全为学校邮箱；不请求微信 openid、昵称或手机号。登录态只保存后端会话和公开身份，不保存密码；页面在 `onShow` 重新读取，退出后不会沿用内存旧值。
- 注册与找回密码共用验证码倒计时：发送后 60 秒内禁止重发，页面卸载停止计时；验证码、密码与确认密码只存在页面内存。注册使用 `redirectTo` 替换登录页，成功后复用 auth 模块统一的 `finishAuthNavigation` 回到发起页；重置密码成功后清理本地会话并返回登录页，邮箱通过查询参数预填，不自动登录。
- 列表与详情使用请求序号丢弃迟到响应，避免快速切换筛选后旧结果覆盖新结果；点评响应在进入页面前校验关键字段与图片地址。
- 地图使用 GCJ-02 坐标：优先读取当前定位，拒绝授权时退回校园中心；用户拖动或缩放结束后节流读取视口四边，点位固定最多 100 条，截断时提示放大地图。标记编号与当次响应数组下标绑定，每次整体替换，避免旧标记跳错店铺。关键词搜索走站内目录接口而非视口点位，结果以列表覆盖在地图上，不受当前范围限制；高德外部地点依赖网页端 JS SDK 与密钥代理，不在小程序直接暴露。
- 消息中心复用本人收件箱接口，按 ALL/SYSTEM/COMMENTS/LIKES/FOLLOWERS 分类读取；列表、分类计数、各类未读数和最新系统摘要取自服务端同一快照，浏览不自动已读。公告以 `announcement:{id}` 作为列表键，回复详情通过本人回复定位接口、获赞详情通过本人获赞定位接口重新鉴权读取，通知本身不保存正文，也不执行任意跳转地址。未读红点由消息页按快照回写，其他 Tab 页进入时轻量查询未读数。
- 写点评入口固定在店铺详情，餐厅与食堂统一使用自身 `restaurantId`，评价对象由页面带入，提交前不能换对象。评分使用 0–10、步进 0.5 的滑杆；推荐态度必填推荐、一般或不推荐三态；正文按去首尾空白后的码点计 1–500。照片先读取宽高限制最长边 1200px，再逐级压缩到 300KiB 以内，随后以 `purpose=REVIEW` 上传换取 fileId；失败照片按稳定 key 单独重试或移除，未全部成功时禁止提交。发布沿用后端 `clientRequestId`：内容不变的重试复用原编号，评分、推荐态度、正文或图片变化后换新编号。统一走 `/api/restaurants/{id}/reviews`，回执必须回指同一店铺编号。发布成功返回详情页并重读点评与评分。
- 详情页互动按点评和回复分别批量读取点赞状态，同一页最多 8 条点评，一次请求即可；状态缺失时保持“未知”，不补 0 也不显示未点赞。点赞写入以服务端回执更新计数，不在本地自增；401 只切换页面登录态，已读取的公开点评仍可阅读。
- 回复按游标分页展开，首次进入读取第一页，更多回复原样带回 `nextCursor`，不在前端构造分页位置。发布回复使用按点评缓存的请求号，正文变化后立即丢弃；删除本人回复需二次确认，服务端仍会按归属校验。举报面板在点击时固定目标类型与编号，原因使用固定枚举，说明按码点限制 200；本人内容在本地隐藏入口，服务端再次拒绝自举报。
- 我的点评与收藏共用一个受保护页面，通过 `tab` 参数决定首屏分类。点评读取 `/api/me/reviews` 的店铺分组，只展示本人当前有效点评；收藏读取 `/api/me/favorites` 并保留失效店铺占位，失效项不能打开详情但仍可取消收藏。切换分类、下拉刷新和追加分页统一用请求序号丢弃迟到响应；取消收藏失败只在列表上方提示，成功后按剩余条数回到仍有内容的页码。
- 新店投稿从找店页“添加店铺”进入，未登录时只展示登录卡片，不渲染可编辑表单，避免登录跳转丢失草稿。表单字段与后端 `POST /api/restaurant-submissions` 白名单一致：店名、普通餐厅/食堂、分类、人均类型与金额、地址、GCJ-02 坐标、营业状态、堂食/外卖三态、标签和最多 5 张照片；食堂显式提交空分类，未知人均提交 `null`。位置通过 `wx.chooseLocation` 选择并记录 `locationConfirmed`，已填写地址不会被地图结果覆盖。标签按行拆分，名称、坐标、金额、标签总长和图片编号在本地先校验，最终分类启用、图片用途和重复投稿仍由服务端判定。成功只代表待审申请已受理，页面跳转到“我的投稿”查看进度，不把申请编号当作餐厅编号打开详情。提交使用与点评相同的内容指纹与 `clientRequestId`：内容不变重试复用原编号，字段或图片变化后换新编号。
- 资料纠错复用投稿页并通过 `id` 参数进入：先读取公开店铺详情回填名称、类型、分类、人均、地址、坐标、营业状态、堂食/外卖和标签，再提交完整快照到 `POST /api/restaurants/{id}/change-requests`。历史坐标只用于回填，仍要求用户主动确认或重新选点；已有公开照片不进入 `photoIds`，只提交本次新增图片。资料未成功读取时禁止提交，避免用不完整表单覆盖未展示字段；失败重试沿用同一 `clientRequestId`，内容或目标变化后换号。纠错入口只面向普通餐厅，食堂资料由管理员维护。
- 图片压缩与临时图上传由 `shared/lib/image` 和 `shared/api/files` 提供，点评与投稿共用最长边 1200px、300KiB 的压缩规则，分别使用 `REVIEW` 与 `RESTAURANT` 上传用途；头像使用 `AVATAR` 用途，要求正方形并压缩到 512×512、300KiB 以内，三类绑定关系不能混用。
- 投稿与纠错记录包含列表与详情：列表按服务端状态计数筛选并分页，详情展示原提交与审核通过快照、驳回原因和 0–4 位置附图。附图是私有资源，`<image>` 无法携带认证头，因此先用 Bearer 下载到临时文件再展示，失败按图重试。待审申请可进入修改或确认撤回，被驳回申请可修改后重新提交；修改走 `PUT /api/me/restaurant-requests/{id}`，重提走 `POST /api/me/restaurant-requests/{id}/resubmit` 并生成新申请。详情接口不暴露原附图文件编号，表单必须说明需要重新选择上传；服务端仍会复核申请状态和归属。目标店铺被删除时保留申请快照但不提供跳转，UPDATE 申请也不再提供重提。
- 公开主页以用户编号进入，登录后读取白名单资料、关注人数与关注状态；点评与收藏分别读取 `/api/users/{id}/reviews` 和 `/api/users/{id}/favorites`。收藏 403 时明确显示“私密”，不降级为空列表；关注/粉丝名单由独立页面读取，403 时原样提示私密。关注写入使用 PUT/DELETE 表达目标状态，回执必须回指同一用户且最终状态与请求一致，未确认时重新读取而非乐观更新。自己的主页隐藏关注按钮，自己的关注名单提供取消关注；“我的”展示本人关注/粉丝人数，点评作者与新增关注消息均可进入公开主页。
- 成长页只读取本人成长摘要，等级、经验与门槛完全使用服务端值，不由前端按经验推算；最高级以 `nextLevelThreshold=null` 处理。
- 资料页只读取本人白名单资料，完整邮箱不进入前端缓存；简介草稿只保存在页面内存，退出、换号或重新加载即丢弃。前端按码点计数并做 100 字上限提示，规范化、控制字符与联系方式检查仍以服务端为准；保存回执必须与本页用户一致，失败保留草稿。头像通过微信头像选择器取得正方形图片，先上传 `AVATAR` 临时图，再以 `PUT /api/me/avatar` 绑定；成功后记录本地版本号绕过图片缓存。头像读取是无认证的公开接口，加载失败或 204 时回退用户名首字，不影响其他内容。
- 隐私设置读取收藏可见性与关注/粉丝名单可见性两套接口：收藏单独提交，关注与粉丝共用一次完整提交，不能只写被切换的一项。保存期间禁用全部开关，避免并发写入产生非预期组合；失败时先恢复到上次确认值，再重新读取服务端设置，不把未确认状态当作成功。进入页面与从登录返回时都重新读取，避免沿用其他设备已修改的设置。
- 窗口体系已随服务端下线：小程序删除窗口列表、独立窗口详情、窗口点评、窗口相册及全部 `windowId` 分支。食堂详情直接展示自身资料、相册、收藏、点评与互动，写点评使用自身 `restaurantId`；消息回复、本人点评和公开主页的点评分组也只按 `restaurantId` 跳转。
- 找店首页把关键词、分类、餐厅类型、用餐方式、人均上限、营业状态、是否已有有效点评和排序交给服务端目录接口，筛选变化后从第一页重读，不在当前页二次过滤。随机选店改调 `POST /api/restaurant-picker/candidates`：服务端在完整合格集合上不放回抽取，客户端维护本轮已看 ID 并作为 `excludeIds` 提交，同批其余候选也进入排除列表；“上一家”用 `checkIds` 复核是否仍符合当前条件。范围只提供清水河、沙河和我的位置，选择我的位置时才申请 GCJ-02 定位；预算、评分、分类和就餐方式均由服务端筛选，不沿用首页关键词。
- 近期推荐榜读取 `/api/restaurant-rankings`，校区与周期是唯一可控参数；READY、PREPARING、UNAVAILABLE 三态原样呈现，客户端不重排、不补店，也不把无快照降级为空榜。
- 详情页删除本人点评需二次确认，删除请求返回 204 后整页重读评分与点评，避免自行拼接新评分；当前已加载点评的图片汇总为横向照片墙，预览集合与展示顺序一致。店铺带完整坐标时通过 `wx.openLocation` 交给系统地图展示位置与路线，缺少坐标时不显示入口；食堂同样按自身坐标处理。
- 普通用户侧尚未接入贡献榜、独立点评照片墙页面、目录页距离筛选和高德外部地点搜索；投稿附带点评暂只支持评分、推荐态度和正文，不支持点评图片。管理端页面保持网页专属，小程序不提供管理员操作入口。

## 技术与源码分层

使用Vue 3 Composition API、TypeScript、Vite、Vue Router、Pinia和Axios。工程配置位于`frontend/config`，容器与Nginx配置位于`frontend/deploy`；Vitest负责单元测试，ESLint与Prettier负责静态规范。

```text
src/
├── app/                 启动装配、布局与路由
├── pages/               路由页面，装配业务模块
├── modules/             业务域
│   └── <module>/
│       ├── api/         后端调用及协议投影
│       ├── model/       状态、业务模型和组合式函数
│       ├── ui/          模块组件及样式
│       └── index.ts     对外公开入口
├── shared/
│   ├── api/             HTTP、凭证及通用协议
│   ├── lib/             通用工具、导航和生命周期辅助
│   ├── styles/          全局样式和变量
│   └── ui/              无具体业务归属的复用组件
└── main.ts              浏览器启动入口
```

依赖方向为`main -> app -> pages -> modules -> shared`；跨业务模块通过公开入口协作。shared不依赖业务模块，module不反向依赖pages或app，页面不读取其他模块内部状态。API DTO、表单草稿和展示模型分开，不把后端返回对象直接作为任意组件的可变状态。

`frontend/config/eslint.config.js`限制主要反向导入；模块间公开入口和Store归属仍需代码审查。通用组件只接收props并发送事件，例如公共页头和底部导航由布局传入身份、未读及退出行为，不自行读取认证Store。

## 模块协作

前后端模块名称不必一一对应，前端以交互归属划分：

| 模块 | 职责与对外协作 |
| --- | --- |
| auth | 登录、注册、密码重置、身份恢复及安全回跳；公开表单和登录状态 |
| account | 个人中心、设置、公开主页壳、本人资料及成长展示；装配review和restaurant的本人内容组件 |
| restaurant | 搜索目录、餐厅／食堂详情、相册、收藏、投稿和本人申请；向admin提供资料编辑及只读预览组件 |
| review | 点评编辑、列表、历史、原文与回复详情、本人点评及消息定位；复用同一回复编辑器 |
| community | 用户署名、关注／粉丝与互动入口；与account及review通过公开能力协作 |
| message | 消息分类、收件箱、未读状态及实时变更；调用review或announcement读取来源内容 |
| announcement | 公告协议及共用阅读弹窗；admin装配发布与管理界面 |
| moderation | 举报交互及协议；内容处置结果仍由服务端确定 |
| admin | 审核、商户管理、举报处理、公告和使用统计工作区；共用管理顶栏、侧栏及主题 |
| map | 高德SDK、地图点位与交互、地点选择及外部导航 |
| file | 浏览器图片压缩、上传与文件协议；业务模块管理各自的草稿绑定 |
| system | 系统状态等基础业务展示 |

## 会话、权限与异步状态

App统一启动身份恢复及消息实时状态。`authSession`集中维护凭证和跨标签页同步，auth管理用户身份；密码只留在表单局部状态。注册成功接收正式会话，密码重置只通过模块内存传递一次性登录预填信息，不通过URL传递账号密码。

DefaultLayout等待初次路由及身份恢复完成再装配内容，管理员访问用户端地址会进入工作台。AdminLayout还调用真实管理会话接口验证身份，验证成功才挂载工作区；前端角色判断不替代后端权限校验。统一登录和权限接口见[账号与认证契约](../api/account.md)。

HTTP层对明确的公开读取省略Bearer，私有读取和写入使用凭证。401只清除发起该请求时使用的旧凭证，503保留会话供重试。业务模型对私有响应继续校验账号、对象及白名单字段，不能因浏览器持有令牌就信任任意响应身份。

所有异步业务遵循相同的生命周期边界，具体模型分别维护自己的请求和草稿：

- 固定发起请求时的凭证、目标ID和读取代次；切换账号、目标或卸载时取消读取并使旧代次失效。
- 取消请求不等于服务端写入回滚。成功写入与后续读取失败分别展示，读取重试不能再次执行写操作。
- 同内容发布、投稿和公告失败重试沿用原UUID；内容变化按所属业务重新生成。关键写入期间阻止重复提交及不安全离开。
- 私有正文、编辑草稿、上传队列和Blob URL不写URL或跨账号共享存储；清理资源前区分未绑定临时文件和已提交文件。
- 加载失败不伪装为零分、零经验、隐私关闭或空列表。隐私、收藏、关注等已接入真实接口，前端不以占位数据兜底。

## 导航、来源与页面现场

站内跳转共用`AppLink`，保留链接语义和Enter操作，通过路由导航而不输出原生href；外部导航及原图使用`ResourceLink`校验允许的URL协议后打开目标。交互名称、悬停提示和键盘焦点由组件保留，具体用户行为见[功能说明](../features.md)。

`useReturnNavigation`只接受白名单阅读地址作为来源，优先返回既有历史条目以恢复现场，直达时回退固定目标。`useListRouteState`只在URL保存分页、筛选等展示选项，通过replace避免每次调整增加返回步骤；表单正文、照片和凭证不放URL。

首页连续列表、地图视口及选店结果另由所属业务模型保存本次页面会话的内存现场，恢复规则按对应功能执行；不能把所有页面的状态等同于永久缓存。账号变化和相关成功写入使需要重读的内容失效。

`LeaveConfirmation`统一承载站内编辑离开确认，路由守卫等待用户选择；取消保留草稿，确认后导航。刷新和关闭标签页使用浏览器beforeunload保护，不能由站内弹窗替代。

## 点评、消息定位与弹窗复用

`ReviewEntry`、`ReviewHistory`和`ReviewNotificationDetail`共用`ReviewDiscussion`，后者复用`ReviewDetailOriginal`与`ReplyThread`，不同入口不复制回复编辑器。店铺与历史明确传递所属餐厅ID和原点评ID；个人列表不通过遍历公开店铺接口拼接。

消息详情先验证通知来源，再读取原点评与目标回复。指定回复按ID定位，与后续游标页去重；仅滚动详情内部。消息已读可能替换列表节点，关闭后按稳定消息ID恢复入口。SSE只推动重新读取，不直接作为正文或权限来源。

桌面点评详情为居中原生dialog，手机为全屏详情；背景滚动受控，正文内部滚动，回复输入保持可达。电脑历史与单条详情通过`reviewHistoryHost`提供宿主，再用Teleport移动同一份详情DOM，共用一个模态窗口。返回历史恢复列表滚动和焦点，跨断点移动不重建编辑器，保留回复草稿及失败UUID；手机沿用历史弹层与全屏详情。

全站普通写评由`WriteReviewLink`在当前地址加入一次性writeReview意图，布局装配`ReviewComposer`，餐厅／食堂详情使用自己的固定目标编辑器，避免同时出现两个编辑器。关闭或发布完成留在来源页，发布通知使已挂载列表重读；未登录回跳由auth校验白名单。投稿两步表单有自己的生命周期，不借用普通写评弹窗。

公告阅读由`AnnouncementReader`提供独立dialog，message核对通知与公告ID的一致性后装配。公告撤回或SSE重连触发内容重新校验；业务详情及接口见[通知与公告](../api/notifications.md)。

使用统计由`AdminActivityWorkspace`及独立读取模型装配。可见时定时读取同一份统计快照，切换指标只投影已读取数据；隐藏、离开或换号时取消请求并隔离迟到响应。`ActivityTrendChart`使用SVG展示折线、鼠标／触摸提示和键盘定位，并提供可供辅助技术阅读的数据表；未知日期拆开折线，不补0。读取已接入[统计API](../api/statistics.md)，不将前端角色判断或模拟数据当作服务端统计。auth公开导出`useActivityReporting`，由App统一挂载：仅普通登录用户主动路由访问、登录完成进入用户端或恢复可见触发上报；没有心跳，不缓存“当天已报”而阻止后续恢复采集。初始路由与身份就绪均重新检查，隐藏、换号和卸载取消旧请求，失败不打断浏览。

## 投稿、审核与原位置查看

`RestaurantCorrection`共用店铺资料草稿、附带点评及两类图片队列，两步切换不提前创建申请。`MyContributions`与`useMyRestaurantRequests`消费本人专用协议，已接入待审修改、撤回及驳回重提；不复用管理员私有详情或审核权限。

管理工作区通过props／events接收页面提供的身份和退出行为。审核模型保留当前申请的独立编辑草稿，提交只投影允许维护的字段；终态回执与队列刷新分开处理，刷新失败不重新审核。原始投稿快照和管理员修订资料不互相覆盖。

“店铺已收录”通过`LinkExistingRestaurantDialog`选择目标，在原dialog内装配restaurant公开的`RestaurantManagementPreview`读取管理员授权资料。返回候选列表保留搜索、页码、选择、滚动与焦点；关闭详情取消读取，已删除目标不加载公开相册。共用组件不新增独立查看路由或编辑模式。

## 图片与相册生命周期

正式店铺相册由restaurant拥有，点评图片留在review；不以点评图、未审核图或样例图填补正式相册。目录与地图消费接口返回的封面，不逐店拉点评寻找图片。头像由account设置入口裁剪和压缩，再通过独立头像协议上传。

`useRestaurantAlbum`按游标读取元数据，以有界工作池加载JPEG Blob，优先处理当前选择；分页、元数据空态及单图失败分开处理。切店、卸载释放ObjectURL，旧代次的结果不能创建失去归属的图片URL。

纠错时已有公开相册与新增上传草稿独立，公开图片不进入dirty基线、上传限制或提交photoIds。上传成功不等于业务已绑定，取消仅清理仍未提交的临时文件；提交成功后释放预览，保护已绑定文件。实际文件用途、限制与权限见[文件接口](../api/files.md)。
