# 商户搜索事务 Outbox

2026-11-04：已实现业务事务内记录及单实例定时消费，消费开关默认关闭；本地已完成9562家存量首次回填及全量核验，尚未切换网站ES搜索。

## 单实例消费初版

V23增加`attempts`（失败次数）、`next_attempt_at`（下次执行时间）、`last_error`（脱敏错误类型）、`completed_at`（确认完成时间），保留V22已有任务和状态。消费者不使用PROCESSING，也不设租约或多实例抢任务。

固定延迟调度每批扫描已到执行时间的PENDING任务，逐条执行：读取最新已提交投影→用投影实际版本写现有ES别名→按任务ID和原失败次数条件确认SUCCEEDED。同步失败则增加失败次数、延后执行；达到上限标记FAILED并保留记录。处理一条失败不停止同批其他任务。不在ES请求期间持有MySQL事务。

默认参数：每批20条、批次完成后等待5秒、失败30秒后重试、最多5次失败；可配置值有界校验。停止或崩溃时任务仍为PENDING，重启后重新扫描；AtomicBoolean只防同一JVM内重叠，不支持多个消费实例同时开启。

ES使用固定商户文档ID和严格`external`版本，要求目标为已存在别名（`require_alias=true`），不自动建索引、不强制refresh。409后通过实时GET核对：更高版本且正文身份/版本元数据一致时旧任务可结束；同版本必须完整正文相等才成功（JSON数字按值比较，数组保序）；其他错误进入重试。物理缺失商户不能猜成墓碑。ES成功但数据库确认失败时不错误增加失败次数，下次重放再核对。

启动参数：

```text
ES_ENABLED=true
ES_SYNC_ENABLED=true
ES_SYNC_INDEX_ALIAS=restaurant-search
```

对应`app.search.sync`下可配置`batch-size`、`delay-ms`、`retry-delay-ms`、`max-attempts`、`index-alias`。只有连接开关不会消费；只有消费开关而未配置客户端会导致启动依赖缺失，不能静默跳过。部署前确保别名指向已初始化的v002兼容结构，并只在一个实例开启消费。

FAILED停止自动重试，不自动删除或因调高上限自动恢复。当前无管理重放接口；修复原因后可由明确授权的维护操作将指定失败任务改回PENDING、失败次数归零、下次执行时间设为当前时间、清空错误及完成时间。不要批量重置所有任务。下调上限前应先处置已超过新上限的PENDING任务；扫描只读取低于当前上限的任务。

## 本阶段行为

同一MySQL事务中完成业务资料/统计修改、每店搜索版本推进和Outbox任务插入。记录服务使用`Propagation.MANDATORY`，不允许脱离业务事务单独调用；任务插入失败直接抛错，让外层事务回滚，不能以日志或内存事件代替持久记录。

```text
业务事务开始
  创建商户 / 锁定商户父行
  更新商户资料或点评统计，生成当前搜索投影版本
  INSERT Outbox SELECT 当前商户ID和数据库版本
  继续完成审核、相册或点评回执等业务
全部成功才一起提交；任何一步失败一起回滚
```

记录任务不调用`RestaurantSearchProjectionService`：该组装器使用独立只读事务，只能看到已提交资料。它将由后续消费者在业务事务之外调用。

## 表结构

迁移：[V22](../../backend/src/main/resources/db/migration/V22__restaurant_search_outbox.sql)。表归restaurant模块所有。

| 字段 | 用途 |
| --- | --- |
| `id` | 自增任务标识；不是每店版本，也不是事务提交顺序或可靠水位 |
| `restaurant_id` | 需要重建搜索文档的商户ID，正Long范围 |
| `projection_version` | 产生任务时MySQL中该店的持久版本，必须为正数 |
| `status` | 业务端插入PENDING；消费成功SUCCEEDED，失败达上限FAILED；PROCESSING保留未使用 |
| `created_at` | 排查任务生成时间，不能代替版本号 |

唯一键`(restaurant_id, projection_version)`阻止同一商户同一版本被重复记录。重复键不静默忽略，它意味着业务入口重复记录或版本推进出错，应回滚并暴露问题。V23以`(status,next_attempt_at,id)`索引支持有界到期扫描。

任务只记录重建意图，不保存完整JSON、图片内容、账号、点评正文或审核资料；所有任务都将重建当前完整投影。没有级联外键，避免资料物理删除时顺带抹掉同步任务；后续遇到物理缺失应明确失败，不能猜测为软删除。

## 已覆盖入口

| 入口 | 记录方式 |
| --- | --- |
| 管理员新建 | 商户插入后版本1，标签成功后记一条任务 |
| 管理员完整编辑 | 原SQL递增版本，标签替换完成后记一条任务 |
| 商户软删除、恢复 | 状态与版本修改后记任务，消费者以后按当前投影组装墓碑或完整文档 |
| 新店、纠错审核通过 | 复用商户写服务，仅产生一条；相册发布和审核结果继续在外层同一事务提交 |
| 点评发布、删除及代表评价回退 | review调用restaurant公开统计服务，统计、版本、任务一起保存 |

待审投稿、审核驳回、只读查询、回复、幂等审核/点评重试和重复删除点评不会增加任务。相同内容的完整商户保存沿用现有规则，仍推进版本并记录任务。

## 事务和后续边界

- 同一商户复用现有父行写锁，任务版本通过`INSERT ... SELECT`读取数据库当前值，不能由调用方随意传入。新建行在提交前也由创建事务持有。
- 审核写服务先记任务，随后发布相册；其他事务在整个审核提交前看不到该任务，因此不会读到缺少新封面的半成品。
- 一个任务产生后商户可能继续变更。消费者必须将重新组装文档实际携带的版本用于ES外部版本控制，不能把旧任务版本套到新资料上。
- 本迁移仅创建空表，不为存量商户补任务；直接SQL、历史导入和维护脚本不自动被捕获，后续全量导入、脚本显式补任务和巡检另行实现。
- 初版有定时消费、延迟重试和任务确认；没有租约、多实例协调、自动失败重放或积压告警。只允许单消费实例，未来多副本部署前必须补协调机制。
- 无公开Outbox HTTP接口，网站仍读取MySQL；即使消费成功，也不代表网站搜索入口已切换。ES写入确认后仍有refresh可搜索延迟。
